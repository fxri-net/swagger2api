# 分片余量回填上一桶

> 计划位置：第 3 个（共 3 个）；前置：20261121-唐启云-新增离线产物审计命令；后继：无

## 背景

- 超大命名空间按 `targetRoutes`（300）切片时未复用 `minBucketRoutes`，尾片可能远小于下限：业务仓实测出现 `Part7` 40 条与 `Part4` 43 条。1.3.1 的「小于下限的桶与相邻桶合并」只覆盖桶层、未覆盖分片层，属装箱规则的设计缺陷。
- 这些尾片是可回填的：前一片 300 条 + 尾片 40 条 = 340 条，未超过 `maxRoutes`（450）。

## 实施方案

1. `src/utils/grouping.ts` 的 `planChunks` 装箱后增加余量回填：若最后一片请求数 < `minBucketRoutes` 且与前一片合并后 ≤ `maxRoutes`，则并入前一片，并按合并后的顺序重排 `Part` 编号。
2. 不改变命名空间归属、类名、调用面与类型；仅减少一个分片文件。
3. 同步更新 `docs/config.md` 的分片描述与技能 `references/output.md`；单测覆盖「余量可回填」与「合并后超 `maxRoutes` 不可回填」两种场景。
4. 变更集标 patch，定性为设计缺陷修复（补全分片层对 `minBucketRoutes` 的复用）：条目注明「重新生成的产物会少一个分片文件，需业务仓下次生成时同步」。与文档收敛、审计命令两项的变更集同批发布 1.3.3。

## 影响范围

- `src/utils/grouping.ts`、相关单测、`docs/config.md`、技能 `references/output.md`、变更集。
- 已生成产物不会自动变化；业务仓下次重新生成时 `api:check` 会提示产物过期，属预期。

## 验证方式

- 跑仓库聚合门禁 `pnpm verify`；单测全绿；对含大命名空间的 spec 做生成回归，确认接口面不变、文件数减一。
- `toolkit tasks check` error 与 warn 均为 0。
- 回滚：还原 `planChunks` 与文档段落、删除变更集。

# 全端通用规范（common）

> 归属：common（所有端适用）。条文全文见本节，索引见 index.md。

## C-2. 任务区不出现参考仓库名

`.tasks/` 内文本（任务档正文、归档叙述、frontmatter 字段值）指称外部仓库时，一律用**通用措辞**（如「接入方仓库」「被参考仓库」「姊妹仓」），不得写实名。

- **要求**：书写任务区文本前，凡需提及本仓以外的仓库，一律改用通用称谓；做技术验证 / 对照参考时同样只写「被参考仓库」这类泛称，不列被参考对象的实名清单。判据取「**是否以具体名称指涉某个外部仓库**」；依赖包名（如 `@fxri/toolkit`）、被调接口名与命令名等属本仓事实者照写。
- **反例**：在任务档正文或归档叙述里列举被参考仓库的实名（如「已把 `foo-web`、`bar-service` 的规范升级至最新版」），或把实名当作 frontmatter 字段的示例值——本仓文本随 git 分发后即携带外部仓库的目录命名，而读者只具本仓视角、无从判断该名与本仓的关系。
- **理由**：任务区是仓库自述面，只承载本仓事实；实名指涉外仓既污染本仓文本，又把某次会话偶发的参照对象固化成仓库事实，还随分发外泄无关仓库信息。
- **配套**：与研发流程「跨仓库改动各自归档」配套——后者管「记不记他仓的事」（视角），本条管「写不写他仓的名」（用词），两者同属任务区文本治理，互为补充。

## C-3. 运行时下限与工具链分层

产物兼容与开发工具链是两条独立轴：发布产物只对运行时下限负责，开发 / 构建 / 检查工具按自身引擎要求选版。

- **要求**：新增或升级依赖、系统命令或 CI 步骤时，先判定它属于「发布产物运行时」还是「开发期工具链」。前者必须满足 `engines` 与构建 target 的运行时下限，且源码不得使用下限不支持的 API；后者可以高于下限，但不得进入生产依赖闭包或构建产物，也不得在运行时回归作业中执行。
- **运行时回归**：运行时下限作业必须覆盖真实业务链路（安装产物、生成 / 构建、关键产物断言），不能只做「能安装」冒烟；因工具链限制无法在低版本执行的步骤，须在门禁里显式跳过并写明原因，不得静默省略。
- **反例**：把测试 / 检查工具的引擎要求当成产物要求而抬升运行时下限；或为迁就开发工具而放弃安全修复；或运行时作业跳过核心链路却仍宣称「低版本已验证」。
- **理由**：两者失败模式不同——产物在低版本跑不起来是交付缺陷，开发工具要求更高的版本只是环境约束；混为一谈，要么被迫抬升下限，要么在低版本上留下验证盲区。

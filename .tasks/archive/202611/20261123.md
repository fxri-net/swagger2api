# 修复 clean 清空契约目录导致分组生成失败

> 计划位置：执行期插入任务（第 1.5 个，共 7 个之后按实际归档）；前置：无；后继：无

## 背景

双产物同源比对（接入方 A `tim` 文档）暴露既有缺陷：`output.clean: true` + 分组模式 + 空输出目录时，生成报错
`ENOENT: no such file or directory, open '<dir>/types/index.js'`。

原因：`src/index.ts` 在调用 `generateApi` 前先 `mkdirSync(<dir>/types)`（L778），而 `cleanOutput` 会随 `...datas.config` 传给 swagger-typescript-api，生成器在启动时清空整个输出目录，把预建的 `types/` 一并删掉；随后契约出口 `types/index` 写不进去，后处理 `splitContractOutput` 读该文件失败。目录非空时因生成器重建目录而侥幸不触发。

影响：接入方 A 的 `tim` 文档配置了 `clean: true`，按「先删目录再生成」执行必然失败。

## 实施方案

1. `cleanOutput` 改由本工具执行：先把 `datas.config.cleanOutput` 置 false（不再传给生成器），非 `--check` 时清空输出目录内容但保留目录本身。
2. 清理位置放在 `snapshotOutputFiles` 之前、预建 `types/` 之前，保持既有回滚语义。
3. `--check` 只置 false，不实际清理（临时目录本就是空的）。
4. 单测/门禁：`scripts/verify.mjs` 分组输出步骤补一个「空目录 + clean: true」的生成用例，断言生成成功且 `types/index` 存在。

## 影响范围

- `src/index.ts`（清理时机与传参）。
- `scripts/verify.mjs` 分组输出断言。
- 不改配置模型与清理安全护栏。

## 验证方式

- 复现场景：空目录 + `clean: true` + 分组 js，生成成功且 `types/index.js` 存在。
- `pnpm verify` 40 步全部通过。

## 回滚方案

还原 `src/index.ts` 的清理改动即可；已生成的产物不受影响。

## 20261123-唐启云-配置紧凑序列化与默认值省略

# 配置紧凑序列化与默认值省略

> 计划位置：第 1 个（共 7 个）；前置：无；后继：20261123-唐启云-双产物同源比对工具、接入方 A~E 的 20261123-唐启云-接口配置收敛与产物切ts

## 背景

工具写配置统一用 `JSON.stringify(value, null, 2)`，任何对象都会整块展开；同时把等于默认值的字段一并写出。结果：

- 接入方 6 份 `swagger2api.json` 中，`output.name: "index"`（默认值）在 5 份里冗余出现；接入方 A 的 `tim` 文档把与 `base` 相同的 `mode: "grouped"` 又写了一遍，且该文档项被展开成多行。
- 用户要求：`docs` 里与 `base` 相同的配置一律上提到 `base`；等于默认值的字段不写；配置文件中对象尽可能单行，展开与否交给项目格式化规范，不由工具臆断。

写盘位置：`src/commands.ts` 的 `writeConfig`（L82）与 `writeDocPatch`（L99），`src/utils/upgrade.ts` 的配置/本地层写盘（L704、L819）。

默认值现状（代码取证）：`client` 不配时为 `fetch`（`src/index.ts` L188），`language` 不配时为 `ts`（L185 `toJS: getPKey("--js")`，L259 仅 `language: js` 才置真），`output.mode` 默认 `single`，`output.typeCheck` 默认 `skip`，`output.banner` 默认 `zh`，`output.name` 默认 `index`，`input.timeout` 默认 `0`，`naming.pathPrefixIndex` 未配置即不裁剪（`0` 是有效个性化值，不能删）。

接入方 A/B/C 当前写的是 `language: "js"`、D/E 写的是 `language: "ts"`；用户确认改为默认 `ts`，因此这 5 份配置应直接删掉 `language` 字段（其值即默认）。该变更属接入方配置整理，归第 3 个任务，本任务只保证写盘不再输出默认值。

## 实施方案

1. 新增配置序列化模块（如 `src/utils/config-format.ts`）：
   - `stringifyConfig(value)`：数组元素若是「扁平对象」（值为标量，且单行长度不超过 160 字符）则单行输出，否则逐行展开；对象键顺序保持现有插入顺序，保证幂等。阈值与接入方 prettier `printWidth: 160` 对齐（已核对 5 个接入方仓的 `.prettierrc`），避免工具展开后 prettier 无法再合并。
   - `stripDefaults(config)`：剔除等于默认值的字段；只覆盖已确认「不配置与显式写默认值行为等价」的键：`client: "fetch"`、`language: "ts"`、`output.name: "index"`、`output.mode: "single"`、`output.typeCheck: "skip"`、`output.banner: "zh"`、`input.timeout: 0`。`naming` / `types` / `grouping` 不参与剔除（如 `pathPrefixIndex: 0` 与不配置语义不同）。
2. 抽默认值真源（如 `src/utils/config-defaults.ts`），运行期读取与写盘剔除共用同一常量，避免文档与实现漂移。
3. `writeConfig`、`writeDocPatch`、`upgrade` 的配置与本地层写盘统一改用 `stringifyConfig` + `stripDefaults`；`package.json` 写盘不变。
4. 文档：`docs/config.md` 增「只写个性化配置」一节（默认值不写、`docs` 与 `base` 重复项上提、对象单行由格式化决定）；`docs/cli.md`、`docs/upgrade.md` 同步写盘口径。
5. 测试：单测覆盖 `stripDefaults`（含 `pathPrefixIndex: 0` 不得剔除）、扁平对象单行与超长展开、二次写入幂等；`scripts/verify.mjs` 的一键迁移断言补充「迁移产物不含默认值字段」。
6. 变更集：patch（写盘格式更紧凑、默认值不落盘，行为不变）。

# upgrade 收敛语义重构

> 延续 一键迁移-upgrade（见 archive/202611/20261123.md）
> 计划位置：第 1 个（共 2 个）；前置：无；后继：20261123-唐启云-upgrade收敛文档与技能同步

## 背景

现行 `swagger2api upgrade` 违背需求边界：用户只要「把 `swagger2api` 后面的个性化参数收敛进配置」，脚本名称、数量与位置必须保持不动；但实现按脚本名 `api` / `api:*` 识别，收敛后删除这些脚本、强写 `scripts.api = "swagger2api"`，还删除 `api:check` 并改写仓库内聚合引用（`api:<id>` → 内联 `--target`）。用户已明确：

- `"api"` 只是举例，脚本键名可能是任意名字，不能作为识别或改写依据；
- 唯一可靠信号是命令值里的 `swagger2api ...`；
- `api:check` 是工具后加的脚本，业务仓无人使用，迁移完全不碰；
- 需要一并排查同类与变体问题（前缀、复合命令、CLI 变体、多文档映射等）。

现状取证（`src/utils/upgrade.ts`）：`isGenerateScript` 按名字判定（L489-491）；按 `name.slice(4)` 猜目标并删除脚本、强写 `api`（L651-660）；聚合脚本改写与 `api:check` 删除（L871-918）；`--check` 按名字与字符串判定遗留（L941-946）。`upgrade.test.ts` 与 `scripts/verify.mjs` 的夹具把「删除脚本」固化为正确结果。

## 实施方案

1. **判定改为命令值**：遍历 scripts，凡命令为「直连单条 `swagger2api <args>`」即纳入收敛；脚本键名不参与判定与改写。复合命令（`&&`、`||`、`;`、管道、后台 `&`）、含环境变量赋值、含位置参数（`$1` 等）一律视为人工项、原脚本不动。
2. **跳过非生成用法**：参数含 `--check`，或子命令为 `grouping` / `surface` / `inspect` / `prune` / `config` / `skill` / `upgrade` / `init`、`--version` 时，脚本原样保留。
3. **彻底移除破坏性逻辑**：删除 `isGenerateScript`、按名字取目标、`scripts.api` 强写、聚合引用改写（含 `api:check` 删除）。迁移不新增、不删除、不重命名任何脚本。
4. **目标文档映射（无脚本名可依）**：① 命令中 `--config <旧文件>` 能对应已迁移文档 → 该文档；② 按 `--url` / `--output` / `--name` 与文档唯一匹配；③ 该单元只有一个文档 → 用它；④ 仍无法唯一确定 → 不猜，脚本原样保留并列为人工项。
5. **重写只替换参数、保留前缀**：保留 `npx` / `pnpm exec` / CLI 路径等前缀，仅替换 `swagger2api` 之后的参数；单文档改写为 `swagger2api`，多文档改写为 `swagger2api --target <id>`。
6. **变体修复**：`argsAfterCli` 支持 `swagger2api.cmd` 等平台后缀；复合命令检测补齐 `;`、管道、后台 `&`；未知子命令跳过；参数解析沿用 `tokenizeArgs` 处理引号。
7. **`upgrade --check` 新判据**：只报「旧配置文件仍存在」与「直连生成脚本仍带配置类参数」；`api:*`、`api:check`、聚合引用不再视为遗留；复合/未知脚本仅提示，不阻塞。
8. **门禁与单测**：`upgrade.test.ts` 夹具改用任意脚本名（如 `gen`、`gen:tim`、`audit:api`）证明与名字无关，断言脚本全部保留且参数已收敛；`scripts/verify.mjs` 的「一键迁移」断言同步改为「脚本保留、api 类脚本不再删除、api:check 原样」。
9. **保持既有能力**：`--dry-run` / `--diff` / `--check` / `--yes` / `--restore`、备份与幂等（二次 `--yes` 零改动）行为不变。

## 影响范围

- `src/utils/upgrade.ts`：脚本判定、目标映射、命令重写、`--check` 判据、删除聚合改写。
- `src/__tests__/upgrade.test.ts`、`scripts/verify.mjs`：夹具与断言改为「按命令值收敛、保留脚本」。
- 不改配置文件模型与生成逻辑；不改 `argsToConfig` 的参数映射语义。
- 变更集与文档同步由后继任务处理。

## 验证方式

- `pnpm verify` 40 步全部通过（含单测、一键迁移门禁、能力漂移、文档链接）。
- 临时仓库手工验证：任意脚本名（`gen` / `sync:api` / `x`）、`npx` 与 `pnpm exec` 前缀、复合命令、多文档歧义（保留原脚本 + 人工项）、`--check` 与二次 `--yes` 幂等、备份恢复。
- 迁移后 `package.json` 的脚本键集合与迁移前一致，仅直连生成脚本的参数被收敛。

## 回滚方案

还原 `src/utils/upgrade.ts` 与测试/门禁断言即可；已执行过迁移的仓库不受影响，重新运行旧版本仍按旧行为处理。

## 完成情况

# CI 耗时优化

> 延续 优化 CI 流程对齐姊妹仓范式（见 archive/202609/20260917.md）与 GitLab 运行时作业下载链路加固（见 archive/202611/20261121.md）
> 计划位置：第 2 个（共 2 个）；前置：20261123-唐启云-生成物对象图契约与环守卫；后继：无

## 背景

两端 CI 均通过但偏慢。实测：

- GitHub Actions CI #37 总 5m22s：windows-runtime18 3m10s、windows 2m55s、check 2m05s、runtime-node18 1m54s；Deploy Docs 47s。
- GitLab #769 总 8m35s：runtime18 4m36s、test 2m10s、toolchain:ensure 1m29s、toolchain:spec 0m23s、pages 0m10s；#763 的 runtime18 达 5m00s。

GitLab 的 runtime18 每次下载 Node 18 tarball；GitHub 的 Windows 两个 job 占大半墙钟；GitLab 还有 toolchain 桥接等待。用户要求优化两端 CI。最优解选择：不动 Windows 覆盖、不默认改 ci-templates，先把 GitLab 的 Node 18 重复下载消掉，并清理 GitHub artifact 版本告警。

## 实施方案

1. 固定基线：记录改动前 3 次 GitHub / GitLab 的总耗时与各 job 耗时，作为对比。
2. GitLab：
   - 优先在 `.gitlab-ci.yml` 内缓存 Node 18 tarball 到项目内固定路径（如 `.cache/nodejs`，按版本 + 架构），保留官方包校验，避免每次下载。
   - `toolchain:ensure` 只做测量与记录；涉及 ci-templates 的外部改动不默认纳入，若确需调整另立任务并取得授权。
3. GitHub：

## 20261123-唐启云-生成物对象图契约与环守卫

> 负责人：唐启云　状态：已完成　范围：swagger2api　完成时间：2026-11-23 06:02

# 生成物对象图契约与环守卫

> 延续 产物对象图契约文档化（见 archive/202611/20261122.md）
> 计划位置：第 1 个（共 2 个）；前置：无；后继：20261123-唐启云-CI耗时优化

## 背景

分组产物曾出现 `Api → user → http → Api` 环，下游 `deepMerge` 的 `mix` 分支递归进环导致栈溢出。当前已把模块 `http` 改为不可枚举，但同类风险不止这一处：`--single-http-client` 的 `http` 仍可枚举；`HttpClient.instance` / `securityData` 是普通可枚举字段；`setSecurityData(api)` 可自造环；`Object.assign` 分片门面存在共享实例；`procedure-call.ejs` 渲染时原地改 `query.type` 会污染共享 route。

用户要求：不要局限于已发现的环逐点打补丁，要建立生成物对象图契约并覆盖变体。

## 实施方案

1. 定义契约：生成物的可枚举自有属性只允许「方法 / 叶子数据」；所有回指、内部实例与运行时状态一律不可枚举；文档明确「不要对 `Api` 实例做深合并、`structuredClone`、持久化或当作纯数据序列化」。
2. 模板收敛：
   - `src/templates/api.ejs`：`--single-http-client` 的 `http` 改为不可枚举访问器；检查聚合 `instance` / `securityData` 暴露面。
   - `src/templates/http-client.ejs`：`instance`、`securityData`、`securityWorker`、`secure`、`format` 改为不可枚举（仍可直接访问），避免深合并进入 Axios 图。
   - `src/utils/modular.ts`：核对 bucket / facade 的 `http` 注入与分片 `Object.assign`，保证可枚举图无环、无重复实例。
   - `src/templates/procedure-call.ejs`：改用局部 `queryType` 变量，不回写 `route.request.query`，保证同一 route 多次渲染确定性。
3. 工具守卫：`src/utils/config.ts` 的 `deepMergeConfig` 与 `src/utils/upgrade.ts` 的 `mergeDeep` 用「祖先栈」（进入加入、回溯移除）做环检测，避免全局 `WeakSet` 把共享引用误判为环；遇环返回可读错误，不栈溢出。
4. 运行期回归：用 JS 产物动态加载（TS 产物继续由 tsc 探针覆盖），覆盖单文件、分组、分片、`--single-http-client` 四种形态；断言可枚举键 BFS 无环、`JSON.stringify` 可执行、`http` / `instance` 描述符不可枚举、方法可调用，并覆盖 `setSecurityData(api)` 自引用场景。
5. 在既有「对象图与合并安全」小节上补充剩余可枚举字段与运行期自检口径，不重写契约；同步 `docs/cli.md`、`skills/fxri-swagger2api/references/output.md` 与夹具，新增 `.changeset/object-graph-contract.md`（minor）。

## 非目标

- 不改为让模块持有轻量 client 适配器；当前以「不可枚举 + 运行期回归」为主，`Reflect` / descriptor 视角的结构断环留待有实际证据再评估。
- 不新增 `toJSON` 或序列化快照 API；契约明确「不要当纯数据序列化」。

## 影响范围

- `src/templates/api.ejs`、`src/templates/http-client.ejs`、`src/templates/procedure-call.ejs`、`src/utils/modular.ts`、`src/utils/config.ts`、`src/utils/upgrade.ts`。
- `src/__tests__/`、`fixtures/expected/**`、`scripts/verify.mjs`、文档与技能中的产物约束说明。

## 验证方式

- 四种生成形态的运行期对象图无环、可序列化、关键描述符不可枚举。
- `pnpm verify` 全量通过（含夹具一致性、单测、构建与文档站）。
- 抽样生成物确认模块方法可调用、`api.instance` 行为不变。

## 回滚方案

还原模板与守卫实现、夹具与变更集；生成物在下次生成时恢复旧形态。

## 完成情况

> 负责人：唐启云　状态：已完成　范围：swagger2api　完成时间：2026-11-23 03:32

# 配置模型 v2：单配置与文档列表

> 延续「多目标配置与批量校验」「配置文件命名与发现」（见 archive/202611/20261121.md）
> 计划位置：第 1 个（共 6 个）；前置：无；后继：20261123-唐启云-目标选择交互与-toolkit-对齐

## 背景

当前配置同时存在三套入口：根级扁平字段（`url` / `file` / `output` 字符串等）、`saconfig*.json` 递归扫描、`swagger2api.json` 的 `defaults` + `targets`。用户要求收敛为唯一一份 `swagger2api.json`，根上放公共配置、文档列表逐项覆盖，不再兼容 `saconfig`。

命名评估（不沿用现有名称）：

- 配置粒度保持现状：每个前端应用目录一份 `swagger2api.json`，与 `package.json`、产物同层；不同目录各自独立，不合并成仓库根一份。

- `defaults`：与工具内置默认值、三层配置的「默认层」混淆，语义不唯一；
- `targets`：来自构建系统，且与 `language.target`（输出语言）撞词，用户实际心智是「文档列表」；
- 推荐 `base` + `docs`：`base` 表示所有文档共享的基础配置，`docs` 直接对应「文档列表」。
- 文档项内把 `input` 收敛为 `source`（字符串即 URL 或文件路径，必要时用 `{ url | file, headers, timeout }`）；`client` / `language` 支持字符串简写，内部再归一为对象，避免 `language.target` 与文档列表撞词。

## 实施方案

1. 定义新 schema：根字段只允许 `base`、`docs`、`profiles`；`docs` 必填非空，每项必须有唯一 `id`，`source` 与 `output` 必填；`id` 只允许字母、数字、下划线、短横线，未知根字段报错并给迁移提示。`base` 可放共享的 `client` / `language` / `types` / `naming` / `grouping` 与 `output` 选项（`name` / `mode` / `prune` / `banner` / `typeCheck`），但不允许 `source` 与 `output.dir`；`output.name` 缺省为 `index`，不得包含路径分隔符与扩展名。`source` 为相对路径时按配置文件所在目录解析。
2. 合并规则：`base` 深度合并进每个文档项（对象递归、数组替换）；三层配置中全局层只允许 `base` / `profiles`，项目层定义 `docs`，本地层按 `id` 覆盖或追加文档项；`profiles` 在合并后、环境变量前应用。升级时不得删除 `swagger2api.local.json`。
3. 删除根级扁平归一与 `saconfig` 扫描：移除 `normalizeConfig` 的扁平分支、`scanConfigFiles`、`--config-scan`、`--config-all`、默认 `saconfig.json`、逗号多文件 `--config`；`--config` 只接受单个文件并保留。

# 接入方就地生成安全替换

> 计划位置：独立任务（共 1 个）；前置：无；后继：无

## 背景

为在发版前把接入方仓库的产物换成新版，验证脚本新增 `--in-place` 就地生成模式。首次实测时按「先删除产物目录 → 再拉取文档」执行，三个接入方的文档网关同时返回 503 / ECONNRESET，产物已删除而新产物未生成，只能从 git 恢复。

根因是就地模式缺少失败保护：删除与生成不是原子操作，拉取失败会留下空目录。

## 实施方案

1. `generateConfig` 增加就地模式分支：生成前把每个已存在的产物目录改名为同级的 `.s2a-backup-<时间戳>` 备份，而不是直接删除。
2. 生成与 `--check` 都成功时删除备份；任一步失败时移除本轮新增的产物目录并恢复备份。
3. 备份与恢复都使用同卷改名，避免复制大目录；备份名不进入产物识别，恢复后目录内容与原来逐字节一致。
4. 临时 worktree 模式保持原有「直接删除」行为，行为不变。
5. 帮助文案说明 `--in-place` 会写入真实工作区，且失败会自动恢复。

## 影响范围

- `scripts/business-validate.mjs`：就地生成分支与备份恢复。
- 不进入 npm 包，不改变生成行为，不需要变更集。
- 接入方仓库仅在生成成功时更新产物；失败时保持原状。

## 验证方式

- 成功路径：就地生成后产物为新版本，备份目录不残留。
- 失败路径：把配置指向不可达地址，生成失败后原产物完整恢复，目录内无残留新文件。
- `pnpm verify` 全部步骤通过。

## 回滚方案

移除备份恢复逻辑与 `--in-place` 分支，脚本回到只能在临时 worktree 内执行的状态。

## 完成情况

- `--in-place` 就地模式：生成前逐文件复制备份到系统临时目录，失败时清空内容并逐文件恢复，成功时删除备份。
- 目录改名改为文件级操作：真实仓库的产物目录可能被编辑器等进程占用，目录级改名会 EPERM。
- 成功后按旧横幅清理残留文件并移除空目录，手写文件与当前横幅文件保留。

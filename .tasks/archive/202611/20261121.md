# 产物自适应分桶与命名空间分片

> 计划位置：第 1 个（共 1 个）；前置：无；后继：无
>
> 延续 20261121-唐启云-分组产物对外面兼容（见 archive/202611/20261121.md）：兼容层已落地，但「一命名空间一文件」的粒度不可接受，改为按接口体量自适应拆分。

## 背景

- 现网分布实测：接入方仓 `mg` 1929 条 / 27 个命名空间，其中 `dg_admin` 独占 1736 条；`lc` 1708 条 / 257 个；`base` 1074 条 / 97 个（`inc` 385）；`tim` 391 条 / 6 个（`dg_admin` 272）；接入方仓 1968 条 / 16 个（`home` 943）；接入方仓 187 条 / 11 个；接入方仓 701 / 261 / 261 条。
- 一命名空间一文件导致 接入方仓 `lc` 521 个文件、`base` 199 个文件，属明显过度拆分；小体量产物（187 条）也不需要拆分。
- 硬约束：对外 `request.<产物>.<首段>.<方法>`、类型推导与运行期行为不变；命名空间是调用层级，不能删除或改名。
- 子路径分布实测：`dg_admin` 第二段统一为 `v3`，第三个段起才有区分度（164 类）；`inc` 第二段统一为 `opt`；`home` 第二段即有区分度（114 类）。子分片必须先跳过版本段。

## 实施方案

### A. 三级结构

1. 命名空间（调用单位，固定为路径首段，对外不变）。
2. 桶（物理文件，仅在体量需要时出现）：多个命名空间类放在一个桶文件里。
3. 分片（命名空间内部再拆）：超大命名空间按子分类拆成多个 chunk 文件，类型与运行期合并回同一个命名空间对象。

### B. 阈值与算法（确定性）

- 默认阈值：`minRoutes=150`（低于则只出 1 个模块文件）、`targetRoutes=300`、`maxRoutes=450`、`minBucketRoutes=60`（尾桶小于此并入前一桶）。
- 分桶：总量 ≤ `minRoutes` 出单文件；否则按分类规则（前缀/正则，未命中入 `fallback`）装箱，每桶不超过 `targetRoutes`。
- 子分片：单命名空间超过 `maxRoutes` 时启用；子分类取「命名空间之后第一个非版本段」（跳过 `^v\d+$`），按子分类装箱到 `targetRoutes`；子分类仍超限时按顺序继续切。
- 单命名空间即使超限也保持可调用性；报表中标红并说明实际文件大小。
- 装箱顺序：命名空间按名称码点排序后**顺序装箱**（相邻名称语义相近、结果可预测），不追求最优装载率；超限在边界切分。
- 桶命名：配置分类规则时用分类名；未配置时用「首个命名空间名」占位、冲突追加序号，并在报表中提示「未配置分类，桶名仅作占位」——降级不静默。
- 确定性：桶内类、分片顺序一律按码点排序，同一 spec 两次生成结果一致。

### C. 合并机制（命名空间分片）

- chunk 文件：每个子分类渲染一个类（沿用现有注入式共享请求器）。
- 门面文件：`export class X { constructor(http) { this.http = http; Object.assign(this, new X1(http), ...) } get instance() {...} }`，
  并 `export interface X extends X1, X2, ... {}` 做类型合并；chunk 类只允许公开成员（现有 `http` 已公开）。
- 聚合入口：仍 `new X(this)`，对外成员集与单文件产物一致；`keyof` 仅新增既有 `http`。
- 不使用原型拷贝：箭头方法在实例上，`Object.assign` 直接复制，闭包内的 `http` 与门面相同。

### D. 工具改造

1. 配置：新增 `grouping.split`（阈值 + `categories` + `fallback`）；缺省不启用，保持现有行为。
2. 规划器：命名空间 → 子分类 → 桶/分片，输出确定性计划（同名同 spec 结果一致）。
3. 模板：桶文件渲染多个命名空间类；分片渲染 chunk 类与门面类（含 interface 合并）。
4. 聚合入口/命名/清单/清理/手写护栏：按桶与 chunk 文件扩展，类名跨桶唯一。
5. 报表：`--dry-run --json` 输出 `产物 → 桶 → 命名空间 → 子分类 → 路由数/预估字节`，标注拆/不拆原因与超限项。
6. 门禁：小体量单文件；大体量每桶不超目标；超大命名空间分片后对外成员集与单文件一致；连续两次生成字节一致；版本段跳过生效。
7. 文档与变更集：`docs/guide.md`、`docs/config.md`、`docs/cli.md`；`.changeset/` patch。

### E. 实现要点（评估结论）

1. 相对路径按文件深度计算：分片文件在 `DgAdmin/` 子目录，JS 内联响应类型须为 `import("../http-client")`，模板接收当前文件深度，不写死。
2. 对外面提取必须合并「类 + interface」：分片门面只在 `interface X extends X1, X2 {}` 上声明方法，`scripts/verify.mjs` 与面上的摘要脚本都要读合并接口，否则摘要比对失真。
3. 清单、清理、产物校验支持子路径：`DgAdmin/User.js` 等嵌套文件要纳入命名表、manifest、prune 与 `verifyGroupedOutput`。
4. 方法名唯一性：同一命名空间跨分片必须全局唯一，重复时生成前报错。
5. 子分类递归深度上限：避免把 `{id}` 等路径参数段当成分类。
6. 桶名、目录名、chunk 类名统一进命名表并判重（Windows 大小写不敏感）。
7. 分片门面运行期语义：`Object.assign(this, new DgAdminUser(http), ...)`；chunk 内的 `http` 指向聚合实例，因此替换 `api.instance` 仍会传导到所有分片（下游 legacy 场景已确认）。
8. 关闭 `grouping.split` 即回到当前行为，作为兜底与回滚开关。

# 产物清理安全与可复现

> 计划位置：第 3 个（共 4 个）；前置：20261121-唐启云-分组命名兼容与保留名；后继：20261121-唐启云-配置文件命名与发现

## 背景

- 分组模式的文件集合随 spec 增减，需要清理「上一轮生成过、本轮已不存在」的模块文件，否则旧模块会残留并被业务误引用。
- 现 `output.clean` 直接清空输出目录。下游多数输出目录混放手写适配文件（`axios.ts`、`call.ts`、`declare.ts`、`parse.ts`、`base.ts`、`captcha.ts`），开启即删除手写代码，因此这些仓目前无法使用该能力。保留 `output.clean` 原语义（清空目录，仅适合纯生成目录），另新增按清单清理的 `output.prune` 供迁移使用。
- 实测问题：rc 驱动 + `output.clean=true` 时，临时文档写在输出目录内，生成后被一并清掉，收尾 `unlink` 抛 ENOENT，控制台打印「失败」但退出码仍为 0，既掩盖真实失败又污染日志。
- 下游验收要求：同一份 spec 重跑仓内既有生成命令，产物必须完全一致（可复现）；生成过程不得写入随时间变化的文件。

## 实施方案

1. 生成结束后在输出目录写 `.swagger2api.manifest.json`，记录本轮生成的文件名清单与工具版本；清单随产物提交，作为下一轮清理的基线。
2. 新增 `output.prune`（对应 CLI `--prune-output`）：仅删除上一轮清单内、本轮不再生成的文件；清单外文件（含手写适配层）一律不动；首轮无清单时只打印告警，不删除任何文件。`output.clean` 原语义保持不变。
3. 手写文件护栏（由命名任务移交）：生成前比对上一轮清单，目标模块文件名已存在且不属于清单时终止并给出明确提示，不覆盖手写文件；首轮无清单只告警。
4. 临时文档改落系统临时目录；删除时加存在性判断，消除 ENOENT 假失败；失败计数与退出码口径保持现状（真实失败必须非 0）。
5. 可复现性：聚合入口与清单不含时间戳；`scripts/verify.mjs` 增加「同一夹具连续生成两次，除清单外产物字节一致」断言。
6. 文档与变更集：`docs/config.md` 写明 `output.prune` 语义与清单用途，`docs/cli.md` 补 `--prune-output`；`.changeset/` 新增 patch 变更集。

3. `scripts/toolkit.mjs`：该脚本转发用户传入的参数，不能拼接字符串。Windows 下改为 `cmd.exe /d /s /c toolkit <args>`，参数仍以数组交给 Node 转义，既消除告警也保留注入防护；非 Windows 维持原调用。
4. 在 helper 注释中写明「拼接方式仅用于内部常量参数，含用户输入的调用必须走 cmd.exe 参数数组」，避免后续误用。

## 20261120-唐启云-分组命名通用化与报表补全

> 负责人：唐启云　状态：已完成　范围：swagger2api　完成时间：2026-11-21 00:34

# 分组命名通用化与报表补全

> 计划位置：第 1 个（共 3 个）；前置：无；后继：无

## 背景

- 分组输出的组名直接充当模块名：`src/utils/grouping.ts` 把组名写回接口 `tags`，交由生成器按 tag 产出文件名与类名；`src/utils/modular.ts` 再从产物文件名反推类名与聚合属性名。
- 组名来源是任意用户输入——tag、路径段、显式规则组名，字符集不受控。下游姊妹仓 8 份真实产物实测：860 个不同 tag，其中 234 个含 `/`、5 个以数字开头、2 个含空格、9 组在 NFKC 折叠后重名（半角/全角括号差异）、含顿号与引号、存在纯符号 tag（如 `[-controller]`）、最长 40 字。
- 现有实现的确定性缺陷：
  - `pascalCase` 按 `[^A-Za-z0-9]+` 切分并丢弃非 ASCII 段，中文组名得到空串，聚合入口会产出 `import {  } from "./…"` 这类非法代码；
  - 组名含 `/` 会被当作目录分隔符，产物写错位置；
  - 大小写、全半角折叠后相同的两个组名会互相覆盖文件；
  - 数字开头、TS 保留字、Windows 设备名（`con` / `aux` 等）、超长名均无处理；
  - 反向推导类名与模板内 `pascalCase` 各算一次，天然存在分叉风险。
- 现有冲突处理盘点：路由方法名重复交依赖库处理（模块内追加序号并告警）；聚合类名与 `Api` 撞名时改名为 `ApiModule`；`collectModules` 把 `index` / `data-contracts` / `http-client` / `*Route` 排除在聚合之外。**组级命名冲突没有任何处理**——两个原始组名经依赖折叠后同名会被静默合组，组名恰为 `index` 时模块文件会被聚合入口覆盖。
- 上一轮「模块化输出支持」方案里承诺的组名规范化、`--dry-run --json`、未命中规则清单、新增/删除文件报表均未实现，归档「实施偏差」也未记录，属于知识面缺口。

## 实施方案

1. **自建命名契约，不沿用依赖的命名推导**：新增 `src/utils/naming.ts`，`normalizeGroupName(raw)` 返回 `{ raw, key, fileName, className, property, reason, source }`。`key` 为 NFKC 归一 + 大小写折叠 + 去分隔符的结果，只用于碰撞检测与排序，不进入产物；`raw` 保留原值用于 `preserveTags` 与报表展示。`source` 标记 auto / manual / fallback。
2. **通用命名管线**（不针对单一语种）：
   - 文件名白名单 `[A-Za-z0-9_-]`，其余字符转为分隔并折叠；禁止 `.`、`..`、`/`、`\`、`:` 等路径字符；
   - 分词按 ASCII 词与 CJK/其他文字段分别成词，输出统一为 lowerCamel：词首字母大写、其余小写，禁止连续大写缩写；该形态对依赖的折叠稳定，兜底名同理取 `group<N>` 而非大写开头；
   - 首字符非法（数字、符号）时加固定前缀，类名必须是合法标识符；
   - TS 保留字与聚合属性名保留字（`new`、`delete`、`class` 等）加后缀；
   - Windows 设备名（`con`、`aux`、`nul`、`prn`、`com1-9`、`lpt1-9`）与产物保留名（`index`、`data-contracts`、`http-client`）加后缀；
   - 长度上限 64 字符，超出截断并追加稳定短哈希，保证同一输入多次生成一致；
   - 归一化后为空（纯符号、纯 emoji）时按原始名排序分配稳定组名 `group<N>`。
3. **命名表先行，产物按表渲染**：
   - 按原始组名以码点排序（不用 `localeCompare`，避免跨机器与跨 locale 结果漂移）→ 折叠键去重 → 不同原值同键时分配 `user2`、`user3` 形态后缀，并与已存在的同名组做二次碰撞检测，直到取到空闲名；
   - 折叠只用于判重，**不合并业务组**：半角/全角括号、仅大小写差异的组保持各自独立；
   - tags 写入命名表产出的模块名，原始标签继续经 `param.groupOriginalTags` 回填 JSDoc；
   - 模板类名不再由依赖的 `pascalCase(moduleName)` 决定，改由 `param` 传入命名表中的类名映射渲染；`api.ejs` 与 `route-types.ejs` 同源取用，聚合入口与模块文件同名；
   - 删除「从文件名反推类名」的逻辑；组名占用 `index` 等保留名时由命名表提前加后缀，避免聚合入口覆盖模块文件。
4. **产物校验门**：生成后按命名表核对实际文件名、类名、聚合属性名，任一不一致即报错并指出期望值与实际值；同时断言自有 slug 经依赖折叠后保持不变，把依赖行为从「隐含约束」变成「可检测契约」。若校验门被触发，或后续需要非 camelCase 的文件命名，则升级为「自有 grouped writer / 生成后重命名层」，不再迁就依赖；该升级不在本期实施。
5. **手工覆盖**：新增 `grouping.names`（原始组名 → 期望名），仍走同一管线校验；覆盖值不合规时报错并指出原始组名。该表属项目级配置，写在项目层 rc 并随仓库提交；rc 的段内浅合并意味着本地层写了 `names` 会整表替换项目层，文档须写明这一点，避免个人层误覆盖团队词表。
6. **与既有标签改写的顺序**：当前实现先分组、后执行 `--replace-tags` 的标签改写，分组模式下会把已写入的模块名再次改写（正则可整段命中并替换为空），导致组名丢失。方案要求先做标签改写再分组，分组模式下不再对模块名标签执行替换，并补一条组合用例。
7. **报表补全**：`--dry-run` 输出「原始名 → 文件 / 类 / 属性」映射、每项重命名原因与来源（auto / manual / fallback）、未命中规则清单、预计新增与删除文件；`--json` 输出结构化结果，供脚本消费。命中来源（规则 / tag / path / 兜底）由分组函数直接返回，报表不重复推断。
8. **表外文件处理**：聚合入口只挂载命名表中的模块；输出目录存在表外产物（改名后残留、手工文件）时列入报表并提示 `output.clean`，不静默混入聚合结果。
9. **测试**：合成样例覆盖斜杠、全角括号、中文、数字开头、保留字、Windows 设备名、超长、纯符号、大小写冲突九类；断言同一输入两次生成结果完全一致，且命名表与产物校验门在人为制造偏差时能报错。
10. **文档与变更集**：`docs/guide.md` 分组章节补命名规则与报表说明，`docs/cli.md` 补 `--dry-run` / `--json` 报表口径，`docs/config.md` 补 `grouping.names`；`.changeset/` 新增条目。

# 契约类型名与模块类名冲突

> 计划位置：第 3 个（共 5 个）；前置：20261122-唐启云-请求器声明改为只读；后继：20261122-唐启云-产物对象图契约文档化

## 背景

- 临时 spec 实测暴露出两类「契约名未受保护」的问题：
  1. **契约名与模块类名同名**：schema 名为 `Probe`、分组也归一为 `probe` 时，生成的 `Modules.ts` 同时出现 `import { Probe } from "./types/index"` 与 `export class Probe`。JS 模式靠 `// @ts-nocheck` 压住类型检查，但 `.d.ts` 里同样是重复标识符（编辑器报错）；TS 模式 `typeCheck: enforce` 会剥离 `@ts-nocheck`，esbuild / vue-tsc 直接报 `Duplicate identifier`，**构建失败**。枚举契约是值导入，无法靠 `import type` 规避。
  2. **契约名与底座导出同名**：schema 名为 `HttpClient` 时，`types/index` 会导出该枚举，聚合入口的 `export * from "./types"` 与 `export * from "./client"` 产生同名歧义，ESM 规则下**该名字从根出口静默消失**。实测 `import * as api` 后 `"HttpClient" in api === false`；业务若从 `@/api` 取客户端底座会拿到 `undefined`。`RequestParams` / `ContentType` / `AxiosResponse` / `AxiosRequestConfig` 等同理。
- 现有 `RESERVED_IDENTIFIERS` 只约束**分组类名**，不约束契约名；`guardSpec` 也不做契约重命名。
- 现有 10 个业务产物目录未触发该冲突，属潜在风险。

## 实施方案

1. **根出口显式优先**：聚合入口不再只依赖两条 `export *`；对客户端底座的固定导出补显式 `export`——`HttpClient`、`ContentType`、`RequestParams`、`FullRequestParams`、`QueryParamsType`、`ApiConfig`、`AxiosResponse`、`AxiosRequestConfig`，显式命名优先于 `export *`，保证底座名字始终可达；契约同名时以底座为准，契约本身仍可从 `types` 直接引用。同步调整 `buildAggregateEntry` / `buildAggregateDeclarations` 与 JS 声明产物。
   - 特例：契约名与聚合类名 `Api` 相同时，根出口无法既导出类又导出同名契约（重复导出即语法错误），此类契约在组件侧追加后缀（如 `ApiContract`），并在变更集里点明。
2. **类名冲突改名**：分组命名阶段把「契约类型名集合」并入 `RESERVED_IDENTIFIERS` 的判定——命中时只改类名与文件名，`api.<属性>` 保持不变（沿用现有「与全局类型同名」分支）。契约类型名由最终 spec 的 `components` 键按生成器的同款归一规则（`pascalCase` + `type-prefix` / `type-suffix`）推导。
3. 机械门禁：`scripts/verify.mjs` 增加断言——生成产物中不得出现「同一文件内 import 名与本地声明名相同」；带同名契约的夹具断言模块类已改名且 `api.<group>` 未变；`HttpClient` 同名契约夹具断言根出口仍能取到底座。新夹具固定命名 `fixtures/contract-collision.json`，与任务 1 的夹具区分。
4. 实现顺序：先由最终 spec 算出契约类型名集合，再进入分组命名；单文件模式的命名空间改名复用任务 1 引入的 `onCreateRoute` 钩子，不另造命名通道，避免两处钩子互相覆盖。
5. 文档与技能补「契约名与底座 / 类名冲突的处置口径」；变更集 patch；技能版本递增。

## 影响范围

- `src/utils/naming.ts`（保留标识符集合扩展）、`src/utils/modular.ts`（聚合入口显式导出）、`src/index.ts`（传入契约名集合）、`scripts/verify.mjs`、夹具与单测。
- 仅在存在同名契约时改变类名或补显式导出，其余产物逐字节不变；现有业务仓当前无命中，无需重生成。
- ⚠️ 若某仓确实存在同名契约，类名会变化（`index.d.ts` 的模块字段类型名随之变化），但 `api.<group>.<method>` 调用面不变。

## 验证方式

- 复现夹具：schema `Probe` + 分组 `probe` 的 TS enforce 产物可被 `tsc --noEmit` / esbuild 编译；schema `HttpClient` 的产物中 `import * as api` 能取到底座。

## 回滚方案

移除显式导出与契约名保留集合、删除断言与夹具；产物恢复为当前行为。

## 完成情况

## 20261122-唐启云-聚合属性保留名与单文件命名空间修正

> 负责人：唐启云　状态：已完成　范围：swagger2api　完成时间：2026-11-22 18:22

# 聚合属性保留名与单文件命名空间修正

> 计划位置：第 1 个（共 5 个）；前置：无；后继：20261122-唐启云-请求器声明改为只读

## 背景

- 工具在生成前用 `路径/方法` 覆写 operationId，路由名再由 `route-name.ejs` 走 `_.camelCase`，末尾必带动词，因此**方法级**裸保留字（`constructor`/`http`/`then`）不可达：临时 spec 实测 `/probe/http` → `probeHttpGet`，`node --check` 通过。相关担忧可以从方案中移除。
- 真正可达的缺陷都在**聚合属性（命名空间）层**，已用临时 spec 复现：
  1. **驼峰保留名失效**：`takeProperty` 用 `name.toLowerCase()` 比对驼峰字面量集合，`setSecurityData`、`mergeRequestParams`、`stringifyFormItem`、`createFormData`、`securityData`、`securityWorker` 六项永远不命中。分组模式下路径首段为 `setSecurityData` 时，产物出现 `setSecurityData = new SetSecurityData(this)`，直接覆盖底座方法，`api.setSecurityData(token)` 变成对模块对象调用 → `TypeError`。小写项 `instance` / `request` / `secure` / `format` / `constructor` / `prototype` 才生效（实测 `/request` 生成 `request2`，已被保护）。
  2. **单文件模式完全没有命名空间保留判定**：命名空间键取自路径首段，模板直接输出 `<moduleName> = { … }`。路径首段为 `request` / `setSecurityData` / `instance` 时，产物出现 `request = {`、`setSecurityData = {`，覆盖从 `HttpClient` 继承的成员；`node --check` 仍通过，运行期一调就 `TypeError`，属**静默破坏**。
  3. 手工命名（`grouping.names`）第一轮只登记占用、不查保留名，可手工制造同样的覆盖。
  4. 判重键复核结论（临时 spec 实测）：分组桶文件内**一个命名空间一个类**（同一个桶里 `export class Alpha` 与 `export class Beta` 并存），跨命名空间方法同名不会撞；分片命名空间由门面合并，必须跨分片唯一——现有「按命名空间判重」已正确，**本任务不改判重键**。
- 单文件模式不能靠「改方法名」来规避：生成器的 `getGroupedRoutes` 在组内方法名唯一时会把 `usage` 还原为原始名，保留名后缀会被撤销。正确做法是改**命名空间键**。

## 实施方案

1. 保留名判定统一大小写：`RESERVED_PROPERTIES` 改为全小写存放（或比较两侧统一归一），六个驼峰条目恢复生效；集合内容维持现有语义（`HttpClient` 成员 + `constructor` / `prototype`）。
2. 单文件模式补命名空间保留判定：通过 `hooks.onCreateRoute` 对 `route.namespace` 做与聚合属性一致的改名（命中保留名则追加序号，同命名空间的所有路由同步改名），确保 `Api` 上不会出现覆盖 `HttpClient` 成员的字段；`http` 一并纳入（`singleHttpClient` 场景下同为已有成员）。
3. 手工命名命中保留属性时直接报错，不静默改名、也不放行。
4. 机械门禁（`scripts/verify.mjs` + 单测）：
   - 分组：路径首段 `setSecurityData` → 断言产物为 `setSecurityData2 = new`，且不存在 `setSecurityData = new`；
   - 单文件：路径首段 `request` / `setSecurityData` → 断言产物不出现 `request = {`、`setSecurityData = {`，且改名后的键被同一命名空间的所有路由共用；
   - 分组命名单测补大小写变体（`SecurityData` 等）与手工名报错；
   - 新夹具固定命名：`fixtures/grouping-reserved.json`、`fixtures/single-reserved.json`，避免与后续任务夹具重名。
5. 文档与技能补「聚合属性保留名大小写不敏感、单文件模式命名空间同样受保护」；变更集 patch；技能版本递增。

## 影响范围

- `src/utils/naming.ts`、`src/index.ts`（新增单文件模式的 `onCreateRoute` 钩子）、`scripts/verify.mjs`、命名与路由相关单测与夹具。
- 仅在命中保留名或同名冲突时改变名字，其余产物逐字节不变；现有 10 个业务产物目录当前无命中，无需重生成。
- ⚠️ 修复后若某仓路径首段恰好归一为那六个驼峰名或单文件模式的保留名，聚合属性会改名（`api.<group>` 变化），属修正而非破坏，变更集需点明。

## 验证方式

- `pnpm verify` 全部步骤通过。
- 临时 spec 复现：分组路径 `/setSecurityData/list` 生成后 `api.setSecurityData` 仍为函数；单文件路径 `/request/list` 生成后 `api.request` 仍为函数，`node --check` 通过。

## 回滚方案

还原大小写归一、单文件命名空间钩子与手工名报错，删除新增断言与夹具；产物恢复为当前行为。

## 完成情况

# 产物类型导入与横幅修复

> 计划位置：独立任务（共 1 个）；前置：无；后继：无

## 背景

- 分组 TS 产物把契约类型以值导入写进模块文件，`verbatimModuleSyntax` 项目里开发服务启动即报「does not provide an export named ...」；同一问题还存在于客户端底座的 `RequestParams`（只是类型别名）。
- 产物文件头只有英文横幅；需要可配置语言，默认中文，同时不能破坏既有英文产物的识别（清理、手写护栏、`--check` 都依赖横幅锚点）。
- 分组产物给每个模块实例注入 `http` 指向聚合入口，形成 `Api → 模块 → http → Api` 环；业务侧深合并（如把 `request` 放进配置后 `dgMerge`）会栈溢出，旧单文件产物无此反向引用。

## 实施方案

1. 契约导入按用途分流：TS 产物的模块文件与 `route-types` 只对运行时枚举按值导入，其余纯类型写 `import type`；客户端底座拆成 `ContentType, HttpClient` + `import type { RequestParams }`。JS 产物的声明文件不参与运行期，保持原值导入形态。
2. 新增 `src/utils/banner.ts`：中英锚点常量、语言解析（`output.banner`，缺省 `zh`，非法值告警后回落）、生成头构造、产物文件头改写（只改含锚点的首个注释块，正文锚点不动）。
3. `isGeneratedFile` 同时认中英锚点；聚合入口、分片门面与聚合声明的文件头按语言输出。
4. 模块与门面的共享请求器改为不可枚举注入（`Object.defineProperty`），保留 `module.http` 与门面 `instance` getter 可用性。
5. 校验与测试：`scripts/verify.mjs` 增加「值导入只能引用运行时值」「默认中文横幅」「请求器不可枚举」断言；新增 `banner.test.ts`，调整 `modular.test.ts`。
6. 文档与变更集：`docs/config.md`、`docs/cli.md`、`docs/guide.md` 同步口径；新增 `grouped-type-imports.md`（patch）与 `banner-language.md`（minor）。

## 影响范围
